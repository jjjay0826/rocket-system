# 從零開始認識這個專案

**這份假設你什麼都不知道。**只需要會看 C 語言,不需要懂火箭、不需要懂訊號處理。
讀完大概 20 分鐘,你會知道這個東西是什麼、為什麼要這樣做、以及接下來該看哪裡。

（已經懂的人請直接去 [README.md](README.md) 的路由表。）

---

## 一、這是什麼

**一塊塞在火箭裡的電路板,它唯一的任務是:在正確的時刻放出降落傘。**

火箭往上衝,燃料燒完之後靠慣性繼續爬,爬到最高點(**頂點 / apogee**),然後開始往下掉。
降落傘必須在**接近頂點**的時候放出來:

- **太早放** → 火箭還在高速上升,傘一張開就被扯爛,或者把箭身拉斷
- **太晚放** → 火箭已經掉太快,傘來不及發揮作用,直接砸地

問題是:**火箭沒辦法直接「知道」自己在哪裡。**它只有幾顆感測器,
必須從這些數字**推斷**出「我到頂點了」。這塊板子做的就是這件推斷,
然後在判斷成立時,把一根腳位拉高、點燃一個小火藥、把傘推出艙外。

> 這是**單向、不可撤銷**的動作。點下去就沒有反悔的機會,
> 所以整個專案的設計重點都在「不要判斷錯」。

## 二、一次真實的飛行

2026-08-01 在旭海飛過一次。用真實數字最容易理解時序:

```
 T+0.0s   點火離架     加速度衝到 5.7 g，板子偵測到「動了」→ 進入 LAUNCHED
 T+3.0s   燃料燒完     速度最快，約 155 m/s；之後只剩慣性與空氣阻力
 T+14.5s  ★ 頂點       833.7 m。速度歸零的瞬間
 T+16.0s  ★ ch1 開傘   板子判定「已經在下降了」→ 拉高腳位 1 秒
 T+18.0s  ★ ch2 開傘   ch2 的主判據沒成立，由 18 秒備援計時器接手
 T+18.0s  拖曳傘張開   衝擊 6.1 g
 T+18.5s  主傘張開     衝擊 5.6 g ── 然後失效了（見下）
 T+43.6s  落海         最後一個封包，高度 20 m
```

**ch1 的開傘發生在頂點後 1.5 秒 —— 主判據做對了。**
**但 ch2 的主判據從未及時成立，是靠備援計時器開的傘。**
原因是它的速度估計被污染（見第五節），這也正是備援存在的理由。

那次的失敗發生在傘本身(傘繩扭轉、結構失效),不在電路板。
完整故事在 [flight_161_summary.md](flight_161_summary.md),但你現在還不用讀。

## 三、板子上有什麼

主控是 **STM32F411CEU6**,買現成的 **WeAct「黑丸版」(Black Pill)** 模組,
插在自製的載板上。跑 84 MHz。

```
                    ┌──────────────────────────┐
   氣壓計 BMP585 ───┤ SPI2  (PB13/14/15)       │
   陀螺+加速度計   ─┤ 共用同一條匯流排          │
   LSM6DS3         │                          │
                    │                          │
   SD 卡 ───────────┤ SPI1  (PA4~PA7)          │
                    │                          │      ┌──────────┐
   GPS ATGM336H ────┤ USART2 (PA2/PA3)         │      │ 地面筆電 │
                    │      STM32F411           │      └────┬─────┘
   LoRa E22 ────────┤ USART1  ← 無線電，往地面送 ─ ─ ─ ─ ─ ┘
                    │                          │
   點火腳 PA0 ──────┤ 拉高 = 放電 = 點燃火藥    │
   點火腳 PA1 ──────┤ （兩路，冗餘）            │
                    │                          │
   兩顆 LED ────────┤ PB2 / PB10               │
                    └──────────────────────────┘
```

### 每顆感測器負責什麼

| 感測器 | 量什麼 | 拿來做什麼 |
|---|---|---|
| **BMP585 氣壓計** | 大氣壓力 | 換算成高度。**這是判斷頂點最可靠的來源** |
| **LSM6DS3** | 加速度 + 角速度 | 偵測「離架了」;估算姿態與速度 |
| **ATGM336H GPS** | 經緯度 | 落點定位。**飛行中不可靠**(見下) |
| **E22 LoRa** | — | 無線電,每 0.5 秒往地面送一包資料 |
| **SD 卡** | — | 機上高速記錄(50 Hz),比無線電詳細得多 |

## 四、最核心的一段:怎麼判斷「該開傘了」

這是整個專案的心臟,寫在 `firmware-rocket/Core/Src/main.c`。

判據是 **`(A 且 B) 或 C`** —— 三個條件,兩條路:

| | 條件 | 意思 | 參數 |
|---|---|---|---|
| **A** | 氣壓高度低於「曾到過的最高點」10 公尺 | **我確實在往下掉了** | `DEPLOY_DROP_M = 10.0f` |
| **B** | 估算的垂直速度 < −0.5 m/s,且持續 1.5 秒 | **而且掉了一陣子,不是雜訊** | `DEPLOY_VZ_NEG_THR / _MS` |
| **C** | 離架後滿 18 秒 | **備援:前兩個都壞掉時的保底** | `DEPLOY_TB_MS = 18000UL` |

A 還有一道防呆:最高點必須先超過 20 公尺(`DEPLOY_PEAK_MIN_M`),
否則放在地上時的氣壓雜訊就可能觸發它。

### 為什麼要兩個條件相「且」

因為**單一感測器會騙你**。氣壓計會被亂流、艙內氣壓變化干擾;
加速度積分出來的速度會漂移。兩個都成立才動作,可以擋掉大部分的單點誤判。

### 為什麼還要 C

因為 A 和 B 都可能**完全失效**。C 不看任何感測器,只看時間 ——
只要離架偵測成立過,18 秒後無條件開傘。

> `18` 這個數字是跑了 **81 組模擬**(3 種推力 × 3 種仰角 × 9 種風況)定出來的,
> **不要憑感覺調**。理由寫在記憶與 `tools/fw_logic.py` 的註解裡。

### 飛行狀態機

板子隨時處在五個狀態之一:

```
IDLE ──偵測到 2.5g 持續一段時間──▶ LAUNCHED ──判據成立──▶ DEPLOYING
                                                              │ 腳位拉高 1 秒
                                                              ▼
                                        LANDED ◀──靜止──── DEPLOYED
```

**`LANDED` 是終點,回不去。**這件事在桌上測試時會咬人 ——
一次上電只能測一發。(所以有一段「地面測試專用」的裸脈衝路徑,見 `ManualDeploy_HandleLine`。)

## 五、為什麼有「兩塊板」

**整套系統做兩份,完全獨立** —— 各自的電源、感測器、天線、SD 卡。
兩塊板互不通訊,各自獨立判斷、各自點火。習慣上叫 **ch1** 和 **ch2**。

這聽起來很浪費,但 2026-08-01 那次證明它是整個專案最值得的決定:

**那次的兩次開傘衝擊,各只有一塊板錄到。**
ch1 錄到第一次然後就失聯;ch2 剛好在第一次的時候漏送了一拍。
只有一塊板的話,永遠不會知道發生過**兩次**衝擊,整個失效原因就推不出來。

另一個好處:**兩塊板的差就是量測誤差。**不用預設誰是對的 ——
兩者一致代表可信,兩者差很多代表那個量不能用。實測:

| 量 | 兩板差多少 | |
|---|---|---|
| 頂點高度(**純氣壓**) | 0.3 m | ✅ 可信 |
| 頂點高度(**卡爾曼濾波後**) | 3.5 m | ⚠ 濾波器在增加誤差 |
| 開傘條件 B 的觸發時刻 | **ch1 成立、ch2 從未及時成立** | 🔴 不可信 |

**這就是為什麼開傘判據 A 用純氣壓,而不是用濾波過的數字。**

## 六、三個軟體專案,哪個跑在哪

| 資料夾 | 跑在哪 | 做什麼 |
|---|---|---|
| **`firmware-rocket/`** | 火箭裡那塊板 | 全部的飛行邏輯。**這是重點** |
| **`firmware-ground/`** | 地面那塊板 | 只做一件事:把 LoRa 收到的字串原封不動轉給筆電的 USB。**很簡單,233 行** |
| `sandbox/` | 桌上測試板 | 實驗場。新功能先在這裡驗證過,才准進 `firmware-rocket` |

真正解析資料、畫地圖、按按鈕的**地面站軟體跑在筆電上,不在這個 repo 裡**。

火箭往下送的封包長這樣(每 0.5 秒一包,純文字):

```
T18510 SQ14954 AX+4.445 AY-2.882 AZ+1.891 GX+991.53 ... P918.07 RH775.8 KH789.2 VZ+17.99 GA5.62 ST:2 MOD:F ...
```

| 欄位 | 意思 |
|---|---|
| `T` | 開機後毫秒 |
| `SQ` | 封包序號(拿來算掉了幾包) |
| `AX/AY/AZ` | 三軸加速度(g)。**AX 是箭體長軸** |
| `GX/GY/GZ` | 三軸角速度(度/秒)。**GX 是滾轉** |
| `P` | 氣壓(hPa) |
| `RH` | **純氣壓**算出的相對高度(m) |
| `KH` | **卡爾曼濾波後**的高度(m) |
| `VZ` | 卡爾曼估的垂直速度 |
| `GA` | 合加速度 |
| `ST` | 飛行狀態 0~4 |
| `MOD` | 四顆模組的健康位元 |

格式寫死在 `main.c:1984`(有 GPS 版)與 `:1993`(無 GPS 版)。

## 七、名詞表

看文件時一直會遇到的:

| 詞 | 意思 |
|---|---|
| **頂點 / apogee** | 火箭飛到的最高點,速度歸零那一刻 |
| **離架 / liftoff** | 火箭離開發射軌。板子靠加速度 ≥ 2.5 g 偵測 |
| **開傘 / deploy** | 放出降落傘的動作 |
| **拖曳傘 / drogue** | 先放的小傘,把火箭穩住並減速 |
| **主傘 / main** | 後放的大傘,負責把落地速度降到安全範圍 |
| **遙測 / telemetry** | 飛行中即時傳回地面的資料 |
| **氣壓高度** | 由大氣壓力換算的高度。壓力越低 = 越高 |
| **卡爾曼濾波 / KF** | 把加速度計和氣壓計兩種量測「融合」成一個估計值的演算法。**這個專案裡它表現不好,別太信它** |
| **合加速度 / GA** | 三軸加速度的向量長度。靜止時 = 1.0 g(重力) |
| **滾轉 / roll** | 繞箭體長軸的旋轉 |
| **cond_A / cond_B** | 開傘判據的 A 條件與 B 條件 |
| **HAL** | ST 官方的硬體抽象層函式庫,`HAL_GPIO_WritePin` 之類的 |
| **CubeMX / CubeIDE** | ST 的圖形化設定工具與開發環境。腳位設定改了要用它重新產生程式碼 |

## 八、你的第一個小時:動手

### 1. 打開專案

STM32CubeIDE → `File` → `Open Projects from File System` → 選 `firmware-rocket` 資料夾。

> ⚠ 韌體有一批**尚未實機驗證**的估計器修正(commit `0b1c66b`,見第五節)。
> 程式碼層與飛行資料重放都驗過了,但**沒有人拿真板子編譯燒錄過**。
> 燒錄前先確認編得過,並且**先上台架再上天**。

### 2. 燒錄

ST-Link 接 SWD(PA13 / PA14 / GND),或用 USB-C 走 DFU。

### 3. 接 USB 看它在說什麼

板子會透過 USB 虛擬序列埠印出人類看得懂的狀態,每 0.5 秒一行。
**先確認 `MOD=` 四顆模組都是 1** —— 那代表氣壓計、IMU、LoRa、SD 都活著。

### 4. 桌上測開傘(不要接火藥!)

用**電表**量 PA0 / PA1 兩支腳。指令流程在
[launch_day_reference.md](launch_day_reference.md) 第三部分。

> ⚠ **在裝上火藥之前,先把整套流程在桌上跑順。**
> 這是不可撤銷的動作,沒有第二次機會。

### 5. 玩玩看真實資料

不用有火箭也能練習分析。`tools/` 裡有 2026-08-01 那次飛行用的全套工具:

**原始 log 就在 repo 裡**(`doc/flightdata/`),clone 下來直接就能跑:

```bash
python tools/parse_raw_lora.py doc/flightdata/20260801/raw_ch1_20260801_152419_5e03e520_utc.log --out-dir out
python tools/parse_raw_lora.py doc/flightdata/20260801/raw_ch2_20260801_152419_5e03e520_utc.log --out-dir out
python tools/flight_report.py out/raw_ch1_*_parsed.csv out/raw_ch2_*_parsed.csv --out report.png
```

會產生一張完整的雙板飛行儀表板。用法見 [../tools/README.md](../tools/README.md)。

## 最後:這個專案的三條原則

從實際踩過的坑學到的,值得先知道:

**① 量到的數字和算出來的數字要分開標。**
文件與圖表裡每個數字都註明來源。「感測器讀到 5.62 g」和
「由此推算質量 25.36 kg」是不同等級的東西,不能混著用。

**② 不要用猜的。**
對齊準不準、GPS 可不可信、裁切有沒有切到 —— 全部用**可以重跑的量測**去判,
而且把判據印出來。這個專案裡好幾個錯誤結論,都是「看起來像」造成的。

**③ 兩塊板對等,不預設誰是真值。**
兩者的差就是量測不確定度。這條原則救過整個失效分析。
